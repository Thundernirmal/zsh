# ZSH-046: PTY harness can inherit host FZF_DEFAULT_OPTS_FILE and change case outcomes

| Field | Value |
| --- | --- |
| Status | Open |
| Priority | P2 — suite results depend on the developer's finder configuration, so the same commit can pass or fail on different machines |
| Audit date | 2026-10-01 |
| Audited baseline | c052f7a52ea1f1cb088de1fd30dc22e724491551 |
| Affected surface | `scripts/test-fzf-pty.py` base/short-list cases (shared picker and `short-<layout>-*` fixtures) |
| Evidence | Live reproduction against fzf 0.74.4: hostile `FZF_DEFAULT_OPTS_FILE` fails a case that passes in the same environment without it |

## Summary

The shared-picker harness `_run_case` scrubs a fixed tuple of finder environment variables that omits `FZF_DEFAULT_OPTS_FILE`, while the branch harness `run_branch_case` removes every `FZF_*`/`ZSH_FZF_*` variable. fzf reads `FZF_DEFAULT_OPTS_FILE` directly (introduced in fzf 0.47.0), so a user with `~/.fzfrc` configured (a documented fzf setup) can change the base and short-list cases' behavior — including options the repository does not set, which merge instead of being overridden. The branch cases stay clean under the same environment, so the suite is internally inconsistent and can report machine-dependent passes or failures for reasons unrelated to the code under test.

## Affected code and documentation

- [scripts/test-fzf-pty.py](../../scripts/test-fzf-pty.py): `_run_case` environment scrub (lines 271–299, fixed tuple at 289–299) versus `run_branch_case` prefix scrub (lines 439–442). The child script passes explicit arguments but fzf still merges the environment defaults it reads for itself.
- [GUIDE.md](../../GUIDE.md#required-checks): the required-checks paragraph describes this suite as deterministic CI coverage.

## Trigger and reproduction

Prerequisites: this checkout, Python 3, native fzf (reproduced on 0.74.4), and a host option file that sets any option the case does not override:

```sh
printf -- '--expect=ctrl-x\n' > /tmp/host-fzf-opts
```

```python
# from the repository root
import importlib.util, os, shutil, sys
spec = importlib.util.spec_from_file_location("ptytest", "scripts/test-fzf-pty.py")
m = importlib.util.module_from_spec(spec); sys.modules["ptytest"] = m
spec.loader.exec_module(m)
zsh, fzf = shutil.which("zsh"), shutil.which("fzf")
case = m.Case("wide-ascii-probe", 100, "ascii", False, "select")
for label in ("control (no host file)", "hostile FZF_DEFAULT_OPTS_FILE"):
    if label.startswith("hostile"):
        os.environ["FZF_DEFAULT_OPTS_FILE"] = "/tmp/host-fzf-opts"
    else:
        os.environ.pop("FZF_DEFAULT_OPTS_FILE", None)
    try:
        m.run_case(zsh, fzf, case); print("PASS", label)
    except AssertionError as error:
        print("FAIL", label, str(error).strip().splitlines()[0])
```

Observed:

```text
PASS control (no host file)
FAIL hostile FZF_DEFAULT_OPTS_FILE: multi-selection did not return two rows: CONFIG_CONTEXT=1 CONFIG_PREVIEW=1 CONFIG_MULTI=1 CONFIG_NO_COLOR=0
```

The same environment leaves `fbr-*` branch cases unaffected because their harness removes the variable by prefix. No fixture state, package manager, or credential backend is involved.

## Current behavior and impact

Developers and CI runners with `FZF_DEFAULT_OPTS_FILE` (or another default-option entry point outside the fixed tuple) can see base/short cases fail or, worse, pass for the wrong reasons, while the branch cases behave differently. Failures look like picker regressions and waste triage; the inconsistency also means the suite's coverage claims are weaker than the script suggests. The review audit observed the leak class during the PR review and this filing reproduced it directly.

## Root cause

Two independent isolation routines evolved: `run_branch_case` scrubs by prefix, `_run_case` scrubs a hand-maintained tuple. The tuple covers the variables the repository exports and the common widget variables but not `FZF_DEFAULT_OPTS_FILE`, which fzf reads itself and merges with command-line arguments for options the picker does not set.

## Fix goal and expected behavior

- Both harnesses isolate finder configuration identically: one shared scrub routine removing all fzf-affecting environment entry points (prefix-based like `run_branch_case`, plus any non-prefixed entries the repository knows about).
- Case outcomes must be invariant under any host finder configuration; a self-check should demonstrate that a hostile variable changes nothing.
- Keep the harness stdlib-only and compatible with fzf 0.68.0 and 0.74.3+.

## Implementation constraints

- Keep per-case temporary HOME/XDG isolation and owned process cleanup.
- Do not weaken the fixtures' assertions; this report only fixes environment isolation.
- Keep the suite runnable standalone (`python3 scripts/test-fzf-pty.py`) and in CI with `FZF_BIN`.
- Update GUIDE.md if the coverage description changes (see [ZSH-047](ZSH-047.md)).

## Acceptance criteria

- [ ] A single shared isolation routine is used by both harnesses and removes `FZF_DEFAULT_OPTS_FILE` and every `FZF_*`/`ZSH_FZF_*` entry point.
- [ ] A self-check sets a hostile option file and asserts the base case outcome is unchanged (or the suite documents and enforces why not).
- [ ] `python3 scripts/test-fzf-pty.py` passes with fzf 0.68.0 and 0.74.3, with and without a host option file present.
- [ ] `zsh scripts/run-tests.zsh` passes.

## Validation plan

Refactor the scrub into one helper, add the hostile-environment regression, and run the suite on both supported fzf versions with `FZF_DEFAULT_OPTS_FILE` set and unset; run the required `zsh scripts/run-tests.zsh`; obtain subagent review under the issue repair workflow.
