# ZSH-042: Roomy preview opens below the list at exactly 100 columns

| Field | Value |
| --- | --- |
| Status | Open |
| Priority | P2 — deterministic, user-visible contradiction of the documented 100-column boundary; preview position only, rows and selection stay correct |
| Audit date | 2026-10-01 |
| Audited baseline | c052f7a52ea1f1cb088de1fd30dc22e724491551 |
| Affected surface | Shared picker preview geometry (`roomy` layout) and the responsive preview threshold |
| Evidence | PTY reproduction against native fzf 0.74.4 at widths 99/100/101 |

## Summary

With `ZSH_FZF_LAYOUT=roomy` and a terminal exactly 100 columns wide, the preview opens below the list instead of to the right. The function takes the wide branch (`width >= 100`) and selects `right,55%,border-left,wrap-word,<51(down,45%,...)`, but the `<51` alternative fires because fzf computes a 50-column preview at that boundary. [GUIDE.md](../../GUIDE.md#finder-layout-and-option-precedence) documents `right 55%` for roomy at 100+ columns, so the picker contradicts its own reference table at the first column where the wide layout is supposed to apply. Compact and minimal change over at exactly 100 as documented; only roomy is off by one threshold column.

- [GUIDE.md](../../GUIDE.md#finder-layout-and-option-precedence): lines 231–239 document the boundary table and the resize behavior.

## Trigger and reproduction

Prerequisites: this checkout, Python 3, native fzf 0.68.0 or 0.74.3+ (reproduced on 0.74.4), any terminal width; the harness sets its own PTY size. No package manager, credential backend, or repository state is touched; each case uses a temporary HOME.

```python
# from the repository root
import importlib.util, shutil, sys
spec = importlib.util.spec_from_file_location("ptytest", "scripts/test-fzf-pty.py")
m = importlib.util.module_from_spec(spec); sys.modules["ptytest"] = m
spec.loader.exec_module(m)
zsh, fzf = shutil.which("zsh"), shutil.which("fzf")
for layout in ("roomy", "compact", "minimal"):
    for width in (99, 100, 101):
        case = m.Case(f"probe-{layout}-{width}", width, "ascii", False, "cancel", layout, 2)
        try:
            m.run_case(zsh, fzf, case); print("PASS", layout, width)
        except AssertionError as error:
            print("FAIL", layout, width, str(error).strip().splitlines()[0])
```

Observed on fzf 0.74.4:

| Width | roomy | compact | minimal |
| --- | --- | --- | --- |
| 99 | down (documented) | down (documented) | down (documented) |
| 100 | **down — documented behavior is right 55%** | right | right |
| 101 | right | right | right |

The failing case reports `actual preview orientation is wrong`; the preview renders roughly 92 columns wide below the list instead of roughly 48 columns at the right. Adding a `short-roomy-100-2` case to the short sweep in [scripts/test-fzf-pty.py](../../scripts/test-fzf-pty.py) fails on the orientation check; the same shape under compact or minimal passes.

## Current behavior and impact

Every roomy picker launched at exactly 100 columns lays its preview out below the list even though the wide branch was chosen and the chrome divides the screen for a side preview. Candidate generation, filtering, marked rows, and selected values are unaffected, so the impact is presentation fidelity and trust in the documented boundary table. Users on exactly 100-column terminals get the narrow placement while the documentation states the wide one.

## Root cause

The conditional threshold is a constant proxy for "terminal is at least 100 columns" rather than a measured preview size:

```zsh
preview_threshold=$(( (100 - 3 - horizontal_padding) * wide / 100 ))
```

For roomy this evaluates `(100 - 3 - 4) * 55 / 100 = 51`. fzf(1) applies `<SIZE_THRESHOLD(ALTERNATIVE_LAYOUT)` "only when the size of the preview window is below a certain threshold"; at a 100-column terminal fzf's computed preview size is 50, so `50 < 51` selects the down alternative. At 101 columns fzf computes 51 and the right layout is kept, which is why only width 100 fails. The proxy also duplicates the chrome geometry (hard-coded three-column border reserve plus `horizontal_padding`), so padding or percentage changes silently move the boundary again.

## Fix goal and expected behavior

- At exactly 100 columns, roomy keeps `right 55%`; at 99 columns it stays `down 45%`; 101+ columns are unchanged.
- The threshold must equal fzf's computed preview size at the 100-column boundary for every layout. During review, changing the reserve constant from `3` to `4` produced 50 for roomy while compact (47) and minimal (42) were unchanged and roomy rendered right; the repair should confirm this against both supported fzf versions instead of adopting it blindly.
- The threshold and the chrome padding must not diverge silently: derive one from the other, or pin both with a regression case.
